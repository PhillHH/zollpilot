## Domain-Überblick

Das Modell konzentriert sich auf die **Export-Deklaration** (`Declaration`) als zentrales Aggregat. Eine Deklaration durchläuft verschiedene Status (Entwurf, Abgeschlossen) und enthält **Warenpositionen** (`DeclarationItem`).

Um die Flexibilität des Wizards zu gewährleisten und Schema-Migrationen für MVP-Iterationen gering zu halten, wird ein **Hybrid-Ansatz** gewählt:
- **Relationale Kern-Attribute:** Status, ID, Referenznummern (für Suche/Listen).
- **JSONB-Datencontainer:** Die eigentlichen Fachdaten (Kopfdaten, Transport, etc.) werden als JSON gespeichert. Das ermöglicht flexible Wizard-Schritte ohne ständige Schema-Updates.

**Kernobjekte:**
1.  **Declaration (Root):** Der Vorgang an sich (Kopfdaten + Metadaten).
2.  **DeclarationItem (Child):** Eine Warenposition innerhalb der Deklaration.

---

## Kern-Entities & Felder

### 1. Entity: `Declaration` (Tabelle: `declarations`)

**Zweck:** Repräsentiert eine einzelne Ausfuhranmeldung (den "Vorgang").

| Feldname | Typ | Pflicht | Beschreibung / Validierung |
| :--- | :--- | :--- | :--- |
| `id` | UUID | Ja | Primary Key |
| `tenantId` | UUID | Ja | FK auf Tenant (Multi-Tenancy) |
| `userId` | UUID | Ja | FK auf User (Ersteller/Besitzer) |
| `status` | ENUM | Ja | Default: `DRAFT`. Werte: `DRAFT`, `COMPLETED` |
| `procedure` | ENUM | Ja | Default: `EXPORT`. Werte: `EXPORT` (später erweiterbar) |
| `step` | INT | Ja | Aktueller Wizard-Schritt (0-indexed). Für Resume-Funktion. |
| `data` | JSONB | Ja | Enthält die fachlichen Kopfdaten (siehe unten). |
| `createdAt` | DateTime | Ja | Zeitstempel Erstellung |
| `updatedAt` | DateTime | Ja | Zeitstempel letzte Änderung |

**Inhalt `data` (JSON-Struktur):**
```json
{
  "referenceNumber": "string (optional, eigene Ref)",
  "parties": {
    "exporter": { "name": "string", "address": "string", "eori": "string (opt)" },
    "recipient": { "name": "string", "address": "string" },
    "declarant": { "name": "string", "address": "string" } // Anmelder
  },
  "transport": {
    "mode": "string (z.B. 3 - Straßenverkehr)",
    "nationality": "string (ISO-Code)",
    "identity": "string (Kennzeichen)"
  },
  "general": {
    "destinationCountry": "string (ISO-Code)",
    "exportCountry": "string (ISO-Code)"
  }
}
```

### 2. Entity: `DeclarationItem` (Tabelle: `declaration_items`)

**Zweck:** Eine Warenposition innerhalb der Deklaration. Ausgelagert in eigene Tabelle für bessere Handhabung bei vielen Positionen (1:N).

| Feldname | Typ | Pflicht | Beschreibung / Validierung |
| :--- | :--- | :--- | :--- |
| `id` | UUID | Ja | Primary Key |
| `declarationId` | UUID | Ja | FK auf Declaration (ON DELETE CASCADE) |
| `sequenceNumber` | INT | Ja | Positionsnummer (1, 2, 3...), muss eindeutig pro Decl sein. |
| `data` | JSONB | Ja | Enthält die fachlichen Positionsdaten. |
| `createdAt` | DateTime | Ja | Zeitstempel Erstellung |
| `updatedAt` | DateTime | Ja | Zeitstempel letzte Änderung |

**Inhalt `data` (JSON-Struktur):**
```json
{
  "description": "string (Warenbezeichnung)",
  "commodityCode": "string (Warennummer, 8 Ziffern)",
  "grossMass": "number (in kg)",
  "netMass": "number (in kg)",
  "invoiceAmount": {
    "value": "number",
    "currency": "string (ISO, z.B. EUR)"
  },
  "procedureCode": "string (z.B. 1000)"
}
```

## Status- & Lifecycle-Modell

Ein einfacher linearer Prozess für das MVP:

1.  **`DRAFT` (Entwurf):**
    - Initialer Status nach Erstellung.
    - Alle Felder sind editierbar.
    - Validierung kann fehlschlagen (Daten unvollständig).
    - Wizard kann jederzeit verlassen und fortgesetzt werden.
2.  **`COMPLETED` (Abgeschlossen):**
    - Wird gesetzt, wenn der User im letzten Schritt "Abschließen" klickt UND die Validierung erfolgreich war.
    - Daten sind "frozen" (im MVP readonly).
    - PDF-Download ist verfügbar.

**Übergänge:**
- `*` -> `DRAFT` (Speichern)
- `DRAFT` -> `COMPLETED` (Validierung OK + User Action)

---

## Wizard-/Progress-Modell

Der Fortschritt wird direkt in der `Declaration`-Entity gespeichert:

- **`step` (INT):** Speichert den Index des aktuellen Wizard-Screens (z.B. 0=Start, 1=Kopfdaten, 2=Transport, 3=Positionen, 4=Review).
    - **Frontend:** Nutzt dies, um den User beim Wiedereinstieg auf die richtige Seite zu leiten.
- **Validierungszustand:**
    - Wird **nicht** in der DB persistiert ("is_valid" Flag unnötig).
    - **Validierung erfolgt zur Laufzeit** (Runtime) im Backend beim Versuch, den Status auf `COMPLETED` zu setzen.
    - Frontend validiert zusätzlich per Step (Client-Side) für UX.

---

## PDF-Export-Grundlage

Das PDF wird "on-the-fly" aus den gespeicherten Daten generiert. Es nutzt keine gesonderten Tabellen.

**Mapping:**
- **Kopf:** `Declaration.data.parties`, `Declaration.data.transport`, `Declaration.data.general`
- **Positionen:** Iteration über alle `DeclarationItems` (sortiert nach `sequenceNumber`), Ausgabe von `data.description`, `data.commodityCode`, `data.grossMass`, etc.
- **Fuß:** Erstellungsdatum (`createdAt`), Referenznummer.

---

## Persistenz-Annahmen

1.  **PostgreSQL mit JSONB:** Wir nutzen die Stärke von Postgres, unstrukturierte Daten effizient zu speichern (`data`-Spalten). Dies vermeidet "Spalten-Friedhöfe" (Tabelle mit 150 Spalten, von denen 140 NULL sind).
2.  **Prisma ORM:** Nutzt `Json`-Typ für das Mapping.
3.  **Transaktionen:** Das Anlegen einer Deklaration + erster Position sollte idealerweise atomar sein (für MVP aber vernachlässigbar, da Positionen meist später kommen).

---

## Out of Scope (explizit)

- **Keine Revisionshistorie:** Wenn ein Entwurf geändert wird, werden die Daten überschrieben. Keine Versionierung (`v1`, `v2`).
- **Keine Stammdaten-Referenzen:** `exporter` ist ein JSON-Objekt im Draft, keine Foreign Key auf eine `AddressBook`-Tabelle.
- **Keine komplexen Typen:** Währungen und Einheiten sind Strings/Numbers, keine Lookup-Tables im MVP.
- **Keine Benutzerverwaltung:** `userId` und `tenantId` kommen aus dem Kontext, aber es gibt keine `users` Tabelle, die wir hier modellieren/ändern müssen (existiert bereits im Basis-Repo).

---

## Offene Fragen / Annahmen

1.  **Annahme:** Die maximale Anzahl an Warenpositionen für das MVP ist gering (< 20). Pagination für Items ist daher nicht notwendig.
2.  **Annahme:** Ein "Löschen" von Positionen (Items) ist ein physisches Löschen (`DELETE FROM`), kein Soft-Delete.
3.  **Annahme:** Wir benötigen keine separaten Tabellen für `Parties` oder `Packages` im MVP; JSON-Nesting reicht aus.
