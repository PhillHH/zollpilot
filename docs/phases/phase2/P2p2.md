> # Phase 2 — Prompt 2 (P2p2)
> # Auth Fundamentals: Signup/Login/Logout + Route Guards
> # Ziel: Sichtbare Auth-Funktionalität + geschützte Produkt-Routen.
> # Output: Neuer User → Signup → Login → /declarations → „Meine Fälle“ leer.
>
> ## Rolle
> Du bist **Senior Fullstack Engineer (Next.js App Router) + Security-minded Implementer**.
> Du implementierst Auth **minimal, robust, dokumentiert**. Kein Design, keine Extras.
>
> ## Kontext (bindend aus Phase 2 Prompt 1B / Guardrails)
> 1) **Auth Stack:** Auth.js v5 (NextAuth) + Credentials + bcrypt
> 2) **Session Strategy:** **DB Sessions** via Prisma Adapter (keine JWT Session)
> 3) **Tenancy:** Tenant/Workspace wird beim Signup automatisch erstellt und dem User zugeordnet
> 4) **RBAC Semantik:** ADMIN = Owner, USER = Member (keine neuen Rollen)
> 5) **DB Strategy:** `prisma db push` (Prototyping) bleibt für Phase 2
>

> ## Deliverable A — Prisma: User Password + Minimal Auth-Felder
> 1) Ergänze User um `passwordHash` (bcrypt)
>    - Beachte existierende Daten: Dev/Seed darf nicht brechen.
> 2) Stelle sicher:
>    - User hat `tenantId` (bestehend)
>    - Email uniqueness ist tenant-scoped (falls in Schema so)
> 3) Keine neuen Rollen/Enums einführen. Nutze vorhandene Roles (ADMIN/USER).
>
> ## Deliverable B — Tenant Auto-Create beim Signup (ohne UI)
> Implementiere serverseitig:
> - POST Register:
>   - validiere Email/Password (zod)
>   - erstelle Tenant (neutraler Name, keine Email im Namen)
>   - erstelle User (role: ADMIN, tenantId gesetzt, passwordHash gesetzt)
>   - starte Session (auto sign-in nach signup) ODER redirect zu login (deine Wahl, dokumentieren)
>
> ## Deliverable C — Auth.js (Credentials) korrekt & sicher
> 1) Credentials authorize:
>    - User anhand Email finden (und ggf. tenant-scope sauber lösen)
>    - bcrypt compare
>    - bei Fehlern: generische Fehlermeldung (kein user enumeration)
> 2) Session:
>    - DB Sessions via Prisma Adapter (bereits Guardrail)
> 3) Session payload:
>    - mindestens: user.id, user.tenantId, user.role
>
> ## Deliverable D — Routes & UI
> Erstelle minimal lauffähige Seiten:
> - `/signup` (Form: email, password, confirm password)
> - `/login` (Form: email, password)
> - `/logout` (Button/Action oder in nav)
>
> Nach Login:
> - Redirect auf `/declarations` (oder euer Dashboard, falls vorhanden)
>
> Kein Design, nur funktional.
>
> ## Deliverable E — Route Protection (mehrschichtig)
> 1) `middleware.ts`:
>    - Schütze: `/declarations/**` (und Dashboard, falls vorhanden)
>    - Public: `/`, `/login`, `/signup`, `/api/auth/**`
> 2) Server-side guard:
>    - API routes für declarations müssen auth prüfen (nicht nur middleware)
>    - Unauth: 401 oder redirect (je nach Route-Typ)
>
