## Sprint-1 MVP – 1-Pager

### Zielgruppe
1.  **Export-Sachbearbeiter (KMU):** Erfasst gelegentlich Ausfuhren, benötigt klare Führung durch das Formular, keine Expertenkenntnisse.
2.  **Demo-User (Stakeholder):** Möchte den Flow von "Start" bis "PDF" in einem Durchgang ohne technische Hürden testen.

### Kernproblem
Die manuelle Erfassung von Ausfuhranmeldungen ist oft unstrukturiert, fehleranfällig und unübersichtlich. Nutzer verlieren den Überblick, welche Pflichtdaten fehlen, bevor sie ein gültiges Dokument erhalten.

### Ziel des MVP
Bereitstellung eines **klickbaren, validierenden Assistenten für die Internetausfuhranmeldung (IAA)**. Der Nutzer soll geführt durch den Prozess geleitet werden, Daten zwischenspeichern können und am Ende ein (simuliertes) Ausfuhrdokument erhalten, ohne echte Zoll-Interaktion.

### Hero-Flow (IAA Export)
1.  **Start:** User klickt auf "Neue Ausfuhranmeldung erstellen".
2.  **Kopfdaten:** Eingabe von Versender, Empfänger und Anmeldeart.
3.  **Warenpositionen:** Hinzufügen von mindestens einer Warenposition (Beschreibung, Gewicht, Wert, Warennummer).
4.  **Validierung:** System prüft auf Pflichtfelder (rot/grün Feedback).
5.  **Abschluss:** User klickt "Abschließen & Generieren".
6.  **Ende:** Anzeige einer Erfolgsmeldung und Download-Link für ein generiertes PDF (Mock).

### MVP-Deliverables
1.  **Web-Formular:** Mehrseitiger Wizard (Step-by-Step) für IAA-Daten.
2.  **Datenbank-Persistenz:** Speicherung der Anmeldungen (auch unvollständig) in PostgreSQL.
3.  **Validierungs-Logik:** Client- & Server-Side Checks für Pflichtfelder.
4.  **Übersichts-Liste:** Dashboard mit "Meine Anmeldungen" (Status: Entwurf / Abgeschlossen).
5.  **PDF-Mock:** Generierung eines einfachen PDFs mit den eingegebenen Daten.

## Scope (Was ist IN)

- **Erfassung:**
    - Beteiligte (Versender, Empfänger, Anmelder)
    - Transportdaten (Verkehrszweig, Kennzeichen)
    - Warenpositionen (Beschreibung, Rohmasse, Eigenmasse, Rechnungsbetrag, Statistische Warennummer als Freitext)
- **Logik:**
    - Pflichtfeld-Validierung
    - Einfache Datentyp-Prüfung (Zahlen, Datum)
    - Speichern als "Entwurf" jederzeit möglich
- **UI/UX:**
    - Progress-Bar (Schritt X von Y)
    - Fehler-Highlighting an den Feldern
    - Liste aller angelegten Vorgänge mit Status-Badge
- **Tech:**
    - Speicherung in `CustomsProcedure` Tabelle (neu zu erstellen)
    - PDF-Generierung via Library (z.B. `react-pdf` oder Server-Side)

---

## No-Liste / Out of Scope (Was ist bewusst NICHT drin)

- **Keine echte ATLAS-Schnittstelle:** Keine XML-Generierung, keine Übermittlung an Zoll-Server.
- **Kein User-Management:** Nutzung des Default-Users; keine Registrierung, kein Login-Screen.
- **Keine Stammdatenverwaltung:** Keine Adressbücher oder Artikelstämme; Daten müssen jedes Mal neu getippt werden.
- **Keine Codelisten-Logik:** Keine Dropdowns mit *allen* Zollstellen oder Ländern (nur kleine Auswahl oder Freitext für MVP).
- **Keine komplexe Plausibilitätsprüfung:** Keine Prüfung, ob Warennummer zum Gewicht passt.
- **Keine Abgabenberechnung:** Keine Zölle, keine Steuern.
- **Keine KI:** Keine automatische Klassifizierung von Waren.
- **Kein Mobile Support:** Desktop-Only Layout.

---

## Annahmen

1.  **Default-User reicht:** Wir nutzen den hardcodierten Tenant/User aus dem Seed für alle Operationen.
2.  **Warennummer manuell:** Der User kennt seine 8-stellige Warennummer oder gibt einen Dummy ein.
3.  **PDF-Mock:** Das PDF muss nicht 100% dem offiziellen Formulardesign entsprechen, solange die Daten lesbar sind.
4.  **Ein Verfahren:** Wir unterstützen nur "Ausfuhrverfahren", keine "Wiederausfuhr" oder Sonderregime.

---

## Risiken

- **Fachlich:** Unterschätzung der Pflichtfelder-Menge für eine *valide* IAA (wir beschränken uns auf ein MVP-Subset).
- **Technisch:** PDF-Generierung im Next.js App Router (Server vs Client Components) könnte Zeit kosten.
- **Zeitlich:** Validierungslogik für komplexe Abhängigkeiten könnte den Sprint sprengen (daher: Fokus auf einfache Feld-Validierung).

---

## Abnahmekriterien auf MVP-Ebene

1.  **Flow durchlaufbar:** Ein Nutzer kann eine Anmeldung von Start bis Ende ohne technischen Fehler durchklicken.
2.  **Daten gespeichert:** Nach Page-Reload sind die eingegebenen Daten (auch Entwürfe) noch da (in der DB).
3.  **Validierung greift:** Leere Pflichtfelder verhindern den Abschluss ("Absenden" Button disabled oder Error-Message).
4.  **Ergebnis sichtbar:** Am Ende wird ein PDF generiert/angezeigt, das die eingegebenen Kopf- und Positionsdaten enthält.
